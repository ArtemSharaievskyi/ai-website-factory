## Why the directories accumulated

The pre-Phase-7E leak was deterministic. [`server.test.ts`](../../src/runtime/qa/server.test.ts:1) directly created `.qa-foundation-*` directories with `mkdtemp` under the repository root. The fixture had no ownership marker or run identity, cleanup used direct recursive removal without bounded retry or terminal absence verification, and failure/interruption could bypass finalization. The real server launcher also did not retain a trusted owner token or reliably terminate the Windows npm/Next descendant tree before filesystem removal.

The proven cause classes are `TEST_PROCESS_LEAK`, `CLEANUP_NOT_IN_FINALLY`, `NO_RETRY`, `CHILD_PROCESS_STILL_ALIVE`, and `INTERRUPTED_PROCESS`. `OPEN_HANDLE`, `CLEANUP_FAILURE_SWALLOWED`, and `WINDOWS_LOCK_DELAY` were not asserted as independent causes.

## Ownership contract

The marker is `.factory-qa-workspace.json`, schema version `1`, and `workspaceKind: "QA_FOUNDATION"`. It contains strict schema-bound workspace and QA-run UUIDs, project/version identity, authorized-root SHA-256 identity, creation time, owner PID, owner session UUID, and lifecycle state. Workspace IDs and QA-run IDs are generated by the trusted host runtime, never by model input.

The authorized root is the `QaWorkspaceLifecycle.authorizedRoot` supplied by the Factory QA runtime. Scanning is bounded to immediate direct children with the `.qa-foundation-` prefix. Cleanup rejects repository roots, filesystem roots, traversal, outside paths, incompatible names, invalid markers, root-identity mismatches, and links/junctions resolving outside the authorized root. Prefix matching alone never authorizes deletion.

States are `CREATED`, `ACTIVE`, `CLEANING`, `CLEANED`, `STALE`, and `ABANDONED`. `CLEANED` is terminal and the directory must be absent; no empty shell remains.

## Resource lifecycle

| Stage | Owned resources | Required action | Failure behavior | Result |
|---|---|---|---|---|
| Create/register | Workspace path, marker | Create direct child and write marker before expensive work | Partial creation is bounded and fails closed | Host-owned handle |
| Use | QA run, browser, server | Assert project path and activate marker | Validation failure triggers cleanup | QA executes only in owned path |
| Finalize | Browser/context/page | Close browser first | Cleanup records browser-close failure separately | Browser closed before deletion |
| Stop | Local server and child tree | Stop trusted owner handle; wait for exit | Typed `QA_PROCESS_TERMINATION_FAILED` and deferred cleanup | No deletion while owned process remains |
| Clean | Workspace tree | Inspect links, remove through Node fs abstraction | Retry only bounded transient lock errors | Removal result is typed |
| Verify | Filesystem path | `lstat` and require absence | Never report success on disagreement | `removed=true`, `verifiedAbsent=true` |
| Reconcile | Stale marker/legacy entries | Scan only authorized root and preserve active/unverified entries | Continue after one bounded failure | Idempotent reconciliation report |

Playwright cleanup occurs in `FunctionalQaService` `finally`: browser close, server stop, process-exit verification, workspace removal. Windows escalation is a fixed internal `taskkill /pid <trusted-owned-pid> /t /f` operation invoked only for a host-created process record; arbitrary PID input and model-controlled commands are unavailable. The process exit wait is bounded at 250 ms graceful wait plus a 5 s escalation wait. The workspace retry policy handles only `EPERM`, `EBUSY`, and `ENOTEMPTY`, with at most 4 retries and 25/50/100/200 ms backoff.

Cleanup results are bounded by [`QaWorkspaceCleanupResultSchema`](../../src/runtime/qa/workspace.ts:49-68): workspace/run identity, safe path reference, attempted/stop flags, removal and absence verification, retry count, deferred state, lifecycle state, reason, and typed failure code. The taxonomy includes ownership, path, active-resource, process-termination, retry-exhaustion, cleanup, marker, legacy-ownership, and reconciliation failures.

Success, assertion failure, server-start failure, browser/runtime failure, validation failure, timeout, cancellation, and unexpected exceptions all leave the primary QA outcome intact while recording cleanup separately. A cleanup failure prevents a false healthy lifecycle result and leaves the workspace eligible only for later ownership-verified reconciliation.
